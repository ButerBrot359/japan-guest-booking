# Этап 6: Гостевой фронтенд — где React встречается с бэкендом

Этот разбор короче предыдущих намеренно: React, TypeScript и react-query тебе
объяснять не надо — ты их знаешь. Интересное в этапе 6 не «как устроен фронт», а
**граница**: четыре места, где клиент стыкуется с нашим бэкендом, и в каждом есть
решение, которое видно только если смотреть на обе стороны сразу. Код фронта — в
`frontend/src/`; спека этапа —
`docs/specs/2026-08-20-stage-6-frontend-guest-design.md`. Все ссылки — на реальные
файлы: открой рядом и сверь строки.

## 1. httpOnly cookie на фронте: залогинен, но токена в JS нет

Обычный фронт хранит JWT в `localStorage` и сам кладёт его в заголовок
`Authorization`. У нас — наоборот: токен лежит в **httpOnly** cookie, и JS её не
видит в принципе. Клиент нигде не читает и не пишет токен:

```ts
const res = await fetch('/api' + path, {
  method,
  credentials: 'same-origin', // httpOnly cookie ходит сама, токенов в JS нет
  ...
})
```

`credentials: 'same-origin'` — единственное, что нужно: браузер сам приложит
cookie к запросу. Вход, срок жизни, затирание при soft-delete (этап 5) — всё это
происходит на сервере, код фронта в этом не участвует.

Тогда возникает вопрос: а как фронт вообще понимает, что пользователь вошёл, если
токена в руках нет? Ответ — никак не «понимает» локально, а **спрашивает
сервер**:

```ts
export function useMe() {
  return useQuery({
    queryKey: ['me'],
    // 401 = «не залогинен» — это данные (null), а не ошибка
    queryFn: () =>
      api.get<Me>('/me').catch((e) => {
        if (e instanceof ApiError && e.status === 401) return null
        throw e
      }),
  })
}
```

Здесь ключевой ход — 401 не всплывает ошибкой, а превращается в `null`. «Гость»
— это не сбой запроса, это валидное состояние данных: `me.data == null`. Поэтому
в `App.tsx` весь UI ветвится по `me.data` (`null` → показать `LoginCard`, не
`null` → `ProfileCard`), а не по какому-то отдельному флагу «залогинен».

Симметрично — выход. Удалять на клиенте нечего (токена нет), поэтому logout это
POST на сервер, который затрёт cookie ответом:

```ts
export function useLogout() {
  const qc = useQueryClient()
  return useMutation({
    mutationFn: () => api.post<void>('/auth/logout'),
    onSuccess: () => qc.invalidateQueries({ queryKey: ['me'] }),
  })
}
```

Фронт лишь инвалидирует `['me']` — и `useMe` перечитывает статус с сервера,
получает 401, отдаёт `null`, UI сворачивается к гостевому. Единственный источник
правды о сессии — сервер, клиент его только переспрашивает.

> **Разбор кода:** открой `frontend/src/api/client.ts` — смотри `request` и
> `credentials: 'same-origin'` (строка 17). Открой `frontend/src/api/queries.ts`
> — смотри `useMe` (401 → null, строки 12-22) и `useLogout` (POST +
> `invalidateQueries(['me'])`). Обрати внимание: нигде в `frontend/src` нет ни
> `localStorage`, ни чтения токена — это и есть смысл httpOnly.

## 2. Same-origin через прокси vs CORS

Раз сессия держится на cookie, всплывает второй вопрос границы: cookie ходит сама
только если запрос браузер считает **своим** (same-origin). Поэтому клиент бьёт в
относительный путь, без хоста:

```ts
const res = await fetch('/api' + path, { ... })
```

`/api/calendar`, а не `http://localhost:8080/api/calendar`. Для браузера это тот
же origin, что и страница, — cookie прикладывается, а CORS-preflight не возникает
вообще. Но бэкенд-то реально живёт на другом порту (dev) и в другом контейнере
(прод). Склейку в один origin делает прокси — и в dev, и в проде.

В dev это Vite:

```ts
server: {
  // same-origin вместо CORS: cookie ходит сама, бэкенд не знает про фронт
  proxy: { '/api': 'http://localhost:8080' },
},
```

Страница на `:5173`, запросы `/api/*` Vite молча переправляет на `:8080` — для
браузера всё на одном origin.

В проде тот же контракт держит nginx:

```nginx
location /api/ {
    proxy_pass http://backend:8080;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
}
```

Статика SPA и `/api/` отдаются с одного origin, `/api/` проксируется на контейнер
`backend`. В обоих случаях бэкенд не знает и не обязан знать, что перед ним фронт:
он видит обычные same-origin запросы.

**Почему не CORS?** Можно было бы посадить фронт и бэкенд на разные origin и
настроить CORS. Но наша cookie httpOnly и это единственный носитель сессии, а
cross-origin cookie — это `SameSite=None; Secure`, точный whitelist origin,
preflight на каждый непростой запрос и приключения в Safari. Один origin убирает
всё это разом: браузер считает запрос своим. Цена — прокси нужно держать в двух
местах (Vite и nginx), и оба должны совпадать по правилу `/api` → бэкенд; забудешь
настроить прокси в новом окружении — получишь 404 вместо ответов бэкенда.

> **Разбор кода:** открой `frontend/src/api/client.ts` — заметь относительный
> `/api` без хоста. Открой `frontend/vite.config.ts` — `server.proxy` (строка 10)
> и комментарий «same-origin вместо CORS». Открой `frontend/nginx.conf` —
> `location /api/` (строка 12) и `proxy_pass` на `backend:8080`.

## 3. Граница форматов дат: ISO на проводе, дд/мм/гггг в рендере

На бэкенде дата — это `LocalDate` и ISO-строка `YYYY-MM-DD`. На фронте человек
хочет видеть `01/03/2026` и «Март 2026». Соблазн — форматировать по месту, в
каждом компоненте. Вместо этого весь перевод форматов собран в один модуль
`lib/dates.ts` — единственная **таможня**:

```ts
// Единственная граница форматов: ISO в API и состоянии, дд/мм/гггг и русские
// названия — только здесь, на выходе в рендер. Работаем строками и UTC —
// никаких Date-с-таймзоной для календарных дат.
```

Везде — в state, в запросах, в ключах кэша — дата остаётся ISO-строкой.
Человекочитаемый вид рождается только на выходе в рендер:

```ts
export function isoToRu(iso: string): string {
  const [y, m, d] = iso.split('-')
  return `${d}/${m}/${y}`
}
```

Вторая, менее очевидная часть этой границы — **таймзона**. Календарная дата дома
не имеет времени, но `new Date('2026-03-01')` — имеет: это полночь UTC, и в
локальной зоне восточнее/западнее она «съедет» на соседний день. Для брони это
тихий сдвиг заезда на сутки. Поэтому `dates.ts` нигде не трогает локальные
компоненты Date — только строки и явный UTC:

```ts
function toUtc(iso: string): number {
  return Date.parse(iso + 'T00:00:00Z')
}
```

И третья грань той же границы — **модель дат** совпадает с бэкендом: считаем
ночи, а не дни. Это видно в `pickDay`, когда гость выбирает день выезда:

```ts
if (dayIso <= checkIn) return { checkIn: dayIso, checkOut: null }
// все НОЧИ [checkIn, dayIso) свободны; сам день выезда может быть занят — полуинтервал
const blocked = isoRange(checkIn, dayIso)
  .some((d) => (days.get(d)?.status ?? 'FREE') !== 'FREE')
```

`isoRange(checkIn, dayIso)` — полуинтервал `[checkIn, dayIso)`: проверяются
ночи от заезда до дня выезда, но НЕ сам день выезда. В день твоего выезда уже
может заезжать другой гость — это тот же полуинтервал «ночи, не дни», что и в
модели дат на бэкенде. Граница модели проходит здесь же, во фронтовой логике
выбора.

> **Разбор кода:** открой `frontend/src/lib/dates.ts` — прочитай верхний
> комментарий (строки 1-3), `isoToRu`/`monthTitle` (выход в рендер) и
> `toUtc`/`fromUtc` (строки 10-16, работа в UTC-строках). Открой

## 4. MSW как контрактный мок: тесты ходят «по сети»

Фронтовые тесты можно писать двумя способами. Можно подменить сам `api` заглушкой
— тогда проверишь компоненты, но не проверишь `client.ts`: сериализацию тела,
разбор статусов, превращение ошибок в `ApiError`. Здесь выбран другой путь — MSW
перехватывает настоящий `fetch` на уровне сети и отвечает вместо бэкенда:

```ts
export const handlers = [
  http.get('/api/calendar', () => HttpResponse.json({ days: mockState.days })),
  http.post('/api/auth/login', async ({ request }) => {
    const { phone } = (await request.json()) as { phone: string }
    mockState.me = { phone, name: 'Маша', role: 'FRIEND', ... }
    return new HttpResponse(null, { status: 204 })
  }),
  ...
]
```

Тест гоняет НЕ замоканный клиент, а реальный `client.ts` против фейкового
сервера. Проверяется весь путь запроса, включая то, как фронт разбирает 401, 409
и коды ошибок. `mockState` при этом играет роль мини-БД: логин пишет в него `me`,
`/api/me` его читает — поведение бэкенда воспроизведено достаточно, чтобы гонять
сценарии.

Что делает этот мок именно **контрактным** — одна строка в setup:

```ts
beforeAll(() => server.listen({ onUnhandledRequest: 'error' }))
```

Любой запрос, на который нет хендлера, роняет тест. Фронт не может втихую сходить
на ручку, которой нет в описанном контракте: если тест дёрнул несуществующий путь
или ты опечатался в URL — это громкая ошибка, а не молчаливый 404.

Грабля здесь — **порядок хендлеров**. MSW матчит первым совпавшим, а
`http.delete('/api/bookings/:id')` совпадает и с `/pending` (`:id` = «pending»).
Поэтому в `handlers.ts` конкретный путь стоит ВЫШЕ параметрического:

```ts
http.delete('/api/bookings/pending', () => {
  if (mockState.me) mockState.me.activeBooking = null
  return new HttpResponse(null, { status: 204 })
}),
http.delete('/api/bookings/:id', () => new HttpResponse(null, { status: 204 })),
```

Поставь их наоборот — и отмена pending-брони улетела бы в общий `/:id`, который не
обнуляет `activeBooking` в `mockState`, и тест падал бы загадочно. Это та же
дисциплина, что и у роутов на сервере: специфичное правило регистрируй раньше
общего.

> **Разбор кода:** открой `frontend/src/test/handlers.ts` — смотри `mockState`,
> хендлеры и порядок `delete('/api/bookings/pending')` (строка 48) ПЕРЕД
> `delete('/api/bookings/:id')` (строка 52). Открой `frontend/src/test/setup.ts`
> — смотри `onUnhandledRequest: 'error'` (строка 8).

## Грабли этапа: независимый mutation сам не сбрасывается

Самое ценное, что поймало ревью этапа, — три бага одной природы, и увидеть их
можно, только если помнить: у `useMutation` из react-query состояние
**императивное**. Ошибка или успех живут, пока жив компонент, и не рассасываются
сами при переходе в другой режим. Три места, где это выстрелило:

1. **`LoginCard`** — состояние заявки при повторном логине. Гость ввёл незнакомый
   номер → `login` вернул `UNKNOWN_PHONE`, открылась форма заявки, заявка ушла
   (`request.isSuccess`). Гость правит номер, жмёт «Войти» снова — а старый
   `request` всё ещё `isSuccess`, и на неверный новый номер опять показалось бы
   «Заявка отправлена». Лечение — сбросить перед новым входом:

   ```ts
   onClick={() => {
     // новый вход — прошлая заявка неактуальна
     request.reset()
     setName(''); setMessage('')
     login.mutate(phone.trim())
   }}
   ```

2. **`OtpModal`** — ошибка confirm после resend. Гость ввёл неверный код
   (`confirm.error = INVALID_CODE`), нажал «Отправить новый». Код обновился, но
   старая ошибка `confirm` всё ещё висит на экране. Лечение — `confirm.reset()` в
   `onSettled` резенда (`OtpModal.tsx` строка 75).

3. **`App`** — ошибка create после детура через режим переноса. Гость получил
   ошибку `create` (скажем, пересечение дат), затем ушёл в режим переноса и
   вернулся — старая ошибка `create` всплыла бы в новой шторке. Лечение — общий
   `switchFlow`, который сбрасывает обе мутации на КАЖДОЙ смене режима:

   ```ts
   // смена режима — прошлые ошибки неактуальны
   const switchFlow = (next: Flow) => {
     create.reset()
     reschedule.reset()
     resetSelection()
     setFlow(next)
   }
   ```

Мораль одна на все три: при любом переходе, после которого прошлый результат
мутации теряет смысл, его нужно **явно** сбросить `reset()` — само не рассосётся.
Это фронтовое эхо той же мысли, что и на бэкенде: состояние живёт дольше, чем
кажется, и «прибрать за собой» — отдельная осознанная операция, а не побочный
эффект.

> **Разбор кода:** открой `frontend/src/components/LoginCard.tsx` — `request.reset()`
> в onClick входа (строка 32). Открой `frontend/src/components/OtpModal.tsx` —
> `confirm.reset()` в `onSettled` резенда (строка 75). Открой `frontend/src/App.tsx`
> — `switchFlow` с `create.reset()`/`reschedule.reset()` (строки 48-53).

## Итог этапа

Этап 6 — это не «мы написали фронт», а «мы аккуратно провели границу между
фронтом и уже готовым бэкендом». Сессия держится на httpOnly cookie, поэтому на
клиенте нет токена и «залогинен» — это ответ `/api/me`, а не локальный флаг.
Чтобы cookie ходила сама, фронт и бэкенд склеены в один origin прокси-слоем (Vite
в dev, nginx в проде) — вместо возни с CORS. Форматы и модель дат заперты в одной
таможне `lib/dates.ts`: ISO и UTC внутри, `дд/мм/гггг` на выходе, полуинтервал
ночей — как на бэкенде. А тесты ходят «по сети» через MSW, который падает на
незнакомый запрос и тем держит контракт с бэкендом честным.

Сквозной вопрос, связывающий этап с предыдущими: и на бэкенде (этапы 4-5), и
здесь на фронте всплыла одна мысль в разных обличьях — состояние не прибирается
само. На сервере это был явный атомарный переход и скоупинг WHERE; на клиенте —
явный `reset()` мутации при смене режима. Где ещё в проекте «само не рассосётся»
оказывалось источником бага, и почему явная уборка почти всегда честнее, чем
надежда на то, что старое состояние никто не заметит?
