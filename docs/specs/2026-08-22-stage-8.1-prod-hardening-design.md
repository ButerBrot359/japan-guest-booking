## 1. Rate limiting: servlet-фильтр вместо вызовов в контроллерах

### Сейчас (проблемы)
`LoginRateLimiter.check(request.getRemoteAddr())` вызывается первой строкой в 4 методах (`AuthController.login/verify/adminLogin`, `AccessRequestController.create`). Три дыры:
- за nginx `getRemoteAddr()` = IP прокси-контейнера → все посетители в одном ведре (локаут соседям);
- один общий бакет: спамер формы заявок локаутит логин;
- `@Valid` срабатывает до тела метода → невалидные тела не считаются лимитером.

### Становится

**`SlidingWindowRateLimiter`** (пакет `auth`, переименование/обобщение `LoginRateLimiter`):
- та же логика скользящего окна (deque + synchronized), но ключ — произвольная строка;
- сигнатура: `void check(String key, int limit, Duration window)` — лимит и окно передаются вызывающим;
- `reset()` остаётся (используют тесты);
- **эвикция**: `@Scheduled(fixedDelay = 600_000)` метод `evictEmpty()` — удаляет из мапы ключи с пустыми окнами (под тем же `synchronized` на deque, удаление через `attempts.remove(key, deque)` только если deque пуст).

**`RateLimitFilter`** (пакет `auth`, `OncePerRequestFilter`):
- матчит только POST; группы:
  - `/api/auth/login`, `/api/auth/verify`, `/api/auth/admin-login` → бакет `auth`;
  - `/api/access-requests` → бакет `requests`;
  - остальные пути — пропуск без учёта;
- лимиты: оба бакета — 5 попыток / 1 минута / IP (константы в фильтре);
- ключ: `бакет + ":" + request.getRemoteAddr()`;
- при превышении фильтр сам пишет ответ (до `DispatcherServlet` `@RestControllerAdvice` недостижим):
  `429`, `Content-Type: application/json;charset=UTF-8`, тело `{"code":"RATE_LIMITED","message":"Слишком много попыток — подождите минуту"}`;
- регистрация в `SecurityConfig`: `.addFilterBefore(rateLimitFilter, BotTokenFilter.class)` — раньше всей аутентификации.

**Контроллеры**: вызовы `rateLimiter.check(...)` и поля `LoginRateLimiter` удаляются из `AuthController` и `AccessRequestController`. Исключение `RateLimitExceededException` и его хендлер в `GlobalExceptionHandler` удаляются, если не остаётся ни одного вызывающего (фильтр кидать исключение не будет — пишет ответ сам).

**XFF**: в `application.yml` добавляется `server.forward-headers-strategy: native` — за nginx (который шлёт `X-Forwarded-For`) `getRemoteAddr()` возвращает реальный IP клиента; при прямом доступе (dev) поведение прежнее. Спуфинг XFF при прямом доступе к порту бэкенда не считаем угрозой V1: в проде порт бэкенда наружу не торчит (только nginx), фиксируется как допущение для 8.2.

## 2. Кука: Secure-флаг и TTL из конфига

Статические `AuthController.authCookie`/`noContentWithCookie` переезжают в компонент **`AuthCookies`** (пакет `auth`):

```java
@Component
public class AuthCookies {
    private final boolean secure;      // app.cookie.secure, дефолт false
    private final Duration ttl;        // Duration.ofDays(app.jwt.ttl-days)
    public ResponseCookie authCookie(String value, Duration maxAge) { ... httpOnly, SameSite=Lax, path=/, secure(secure) ... }
    public ResponseCookie session(String token) { return authCookie(token, ttl); }
    public ResponseCookie expired() { return authCookie("", Duration.ZERO); }
}
```

- `app.cookie.secure: false` добавляется в `application.yml` (прод включит через env в 8.2);
- `COOKIE_TTL` (30 дней хардкодом) удаляется — TTL берётся из существующего `app.jwt.ttl-days` (кука и токен живут одинаково);
- потребители: `AuthController` (4 места) и `GlobalExceptionHandler.userGone` (затирающая кука) переходят на инжект `AuthCookies`; статические методы из `AuthController` удаляются.

## 3. Admin-login: dummy-hash против тайминг-канала

Сейчас при неизвестном телефоне/не-админе BCrypt не вызывается — время ответа выдаёт, существует ли номер. Становится: в `AuthController` константа `DUMMY_HASH` (валидный BCrypt-хеш случайной строки, сгенерированный один раз и захардкоженный с комментарием); ветка «пользователь не найден/не подходит» прогоняет `encoder.matches(body.password(), DUMMY_HASH)` и лишь затем кидает `InvalidCredentialsException`. Ответ остаётся единым 401.

## 4. BotTokenFilter: path-guard + constant-time

- ранний выход: `if (!request.getRequestURI().startsWith("/api/bot/")) { chain.doFilter(...); return; }` — фильтр больше не бежит на чужих путях (заодно закрывает старую заметку «JWT-кука перезаписала бы ROLE_BOT»);
- сравнение: `MessageDigest.isEqual(token.getBytes(UTF_8), header.getBytes(UTF_8))` вместо `String.equals` (constant-time); пустой конфиг-токен по-прежнему закрывает эндпоинт (проверка `token.isBlank()` до сравнения, header `null` → не совпадает).

## 5. Миграция V9 + чистка PENDING_OTP из кода

`V9__drop_pending_otp_outbox_attempts.sql`:

```sql
-- PENDING_OTP мёртв: флоу удалён в 6.6, строки отменены в V8. Чистим констрейнт.
ALTER TABLE bookings DROP CONSTRAINT bookings_status_check;
ALTER TABLE bookings ADD CONSTRAINT bookings_status_check
    CHECK (status IN ('CONFIRMED', 'CANCELLED', 'COMPLETED'));

-- Счётчик попыток публикации: ядовитая строка не должна вечно блокировать очередь.
ALTER TABLE outbox ADD COLUMN attempts INT NOT NULL DEFAULT 0;
```

(GiST-исключение и `one_confirmed_booking_per_user` уже без `PENDING_OTP` с V8/V1 — проверено.)

Java: значение `PENDING_OTP` удаляется из enum `BookingStatus`. Компилятор укажет хвосты: ветка в `BookingsExcelWriter.statusRu` (удалить) и упоминания в `BookingRepositoryTest` (подчистить). Фронтовый тип `BookingStatus` в `frontend/src/api/types.ts` PENDING_OTP не содержит — фронт не трогаем.

## 6. Outbox: счётчик попыток и чистильщик

`OutboxPublisher.publishPending`:
- выборка получает `and attempts < 5`;
- при ошибке отправки: `update outbox set attempts = attempts + 1 where id = ?`; если новое значение достигло 5 — `log.error("outbox id={} исчерпал попытки, строка пропущена", ...)`, иначе прежний `log.warn`; затем `return` (порядок остальных сохраняется, как сейчас);
- успешная отправка — без изменений.

Новый метод там же: `@Scheduled(cron = "0 0 4 * * *")` (раз в сутки, 04:00 JST — таймзона шедулера = таймзона JVM контейнера, укажем `zone = "Asia/Tokyo"` явно) `cleanupPublished()`: `delete from outbox where published_at < now() - interval '7 days'` + `log.info` с числом удалённых. Сырые OTP-коды перестают жить в дампах вечно; 7 дней достаточно для отладки.

## 7. Мелочь из бэклога: лог повышения роли сидером

В админ-сидере (ApplicationRunner, upsert админа из конфига): если существующий пользователь был `FRIEND` и становится `ADMIN` — `log.warn("Пользователь {} повышен до ADMIN сидером", phone)`.

## Тестирование (`./mvnw test` из `backend-api/`)

- **RateLimitFilter** (интеграционные, MockMvc): 6-й POST `/api/auth/login` за минуту → 429 с `code=RATE_LIMITED`; бакеты независимы (исчерпанный `auth` не мешает `/api/access-requests`); невалидное тело (`{}`) тоже расходует попытку; GET/другие пути не считаются. Существующие тесты, дёргающие логин >5 раз, — проверить и при необходимости добавить `SlidingWindowRateLimiter.reset()` в setup (как делалось с `LoginRateLimiter`).
- **SlidingWindowRateLimiter** (юнит): окно скользит (MutableClock уже есть в тестах лимитера), `evictEmpty` удаляет пустые ключи и не трогает живые.
- **AuthCookies**: с `app.cookie.secure=true` (тест с `@TestPropertySource`/property override) `Set-Cookie` содержит `Secure`; дефолт — не содержит; `Max-Age` куки соответствует `app.jwt.ttl-days`.
- **Admin-login**: существующие тесты 401 остаются зелёными (dummy-hash не меняет контракт).
- **BotTokenFilter**: валидный токен на `/api/bot/**` даёт доступ (существующие тесты); НОВЫЙ: валидный `X-Bot-Token` на не-bot пути (например `GET /api/admin/bookings`) НЕ даёт доступа → 401.
- **V9/enum**: полный прогон компилируется и зелёный после чистки.
- **Outbox** (интеграционные, в существующем стиле outbox-тестов): строка с `attempts=5` не публикуется, следующая за ней — публикуется; ошибка отправки инкрементит `attempts` (мок/остановленная Kafka — по образцу существующих тестов; если образца нет — юнит с моком KafkaTemplate); `cleanupPublished` удаляет опубликованную строку 8-дневной давности и не трогает неопубликованную/свежую.
