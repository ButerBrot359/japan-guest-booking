# Этап 5: Админ-API + заявки на доступ — дизайн

Дата: 2026-08-20. Статус: одобрен владельцем (брейншторминг 2026-08-20).
Родительская спека: `docs/specs/2026-08-13-japan-guest-booking-design.md`
(§3.1, §3.4, §3.5, §5, §6, §8).

## 1. Цель и скоуп

Админ (владелец) через API управляет всем хозяйством: блокирует даты,
отменяет и переносит любые брони без OTP, ведёт белый список, рассматривает
заявки на доступ. Незнакомец с сайта подаёт заявку; админ получает
уведомление в Telegram. Попутно закрываются переносы из ревью этапов 1–4.

**Продуктовый контекст** (со слов владельца): сайт публичный — ссылка
раздаётся в соцсетях владельцем. Флоу новичка: вводит номер на сайте →
логин отвечает «номер не найден» → фронт (этап 6) показывает форму заявки
(имя, комментарий, номер) → заявка уходит админу. То, что «номер не
найден» раскрывает членство в белом списке, — осознанный выбор для сайта
«для своих». Следствие: `POST /api/access-requests` — самый обстреливаемый
эндпоинт, rate limit по IP обязателен.

**В скоупе:** блокировки дат (CRUD + участие в проверках пересечений через
advisory lock); админ-операции над бронями (список, отмена, перенос — без
OTP, с уведомлением гостя); белый список (список, ручное добавление,
soft delete); заявки на доступ end-to-end (+ событие
`ACCESS_REQUEST_RECEIVED` и рендер в боте); русские даты в текстах бота;
`@PreAuthorize` поверх URL-правила; переносы из ревью: проверка
`blocked_periods` в create/reschedule, доменные not-found,
`AccessDeniedException` → 403, `/api/me` удалённого пользователя → 401,
явная отмена гостем своей PENDING_OTP-брони, прямой тест
`findOverlapping`.

**Вне скоупа:** frontend (этапы 6–7), сброс пароля админа, пагинация
списков (масштаб «друзья» — YAGNI), хранение контактов незнакомцев для
авто-приглашения, SMS.

## 2. Данные

- **Миграция V3:** `ALTER TABLE users ADD COLUMN deleted_at TIMESTAMPTZ`
  (NULL = активен). Больше ничего: `blocked_periods` и `access_requests`
  созданы в V1 и подходят как есть.
- **Soft delete:** телефон в `users` уникален, поэтому повторное одобрение
  ранее удалённого человека **реактивирует** старую запись
  (`deleted_at = NULL`) — история его броней возвращается к нему.
  Все проверки «жив ли» — `deleted_at IS NULL`: логин, JWT-фильтр,
  `findByPhone` при онбординге контакта и заявках.
- **Осознанный выбор:** «жив ли пользователь» проверяется пер-эндпоинтно
  (`MeController`, `requireTelegramLinked` и т. п.), а не в JWT-фильтре —
  фильтр остаётся stateless и без похода в БД на каждый запрос, а значит
  каждый новый защищённый эндпоинт обязан сам пройти через users-проверку.
- Заявка: `PENDING → APPROVED | REJECTED` (+ `resolved_at`). Одна живая
  PENDING на номер: повторный POST с тем же номером — идемпотентный 201
  без новой записи.

## 3. Пересечения дат и advisory lock

Дыра из ревью этапа 4: create/reschedule не проверяют пересечение с
`blocked_periods`. Exclusion constraint работает только внутри одной
таблицы — пересечение «бронь ↔ блокировка» проверяется кодом, а такая
проверка без синхронизации даёт гонку (двое проверили «свободно» → оба
вставили).

Решение — **транзакционный advisory lock** (`pg_advisory_xact_lock(K)`,
K — одна константа приложения): каждый, кто проверяет пересечение дат и
вставляет/двигает период, сначала берёт замок той же транзакцией. Берут
его: создание брони, подтверждение не нужно (даты уже удержаны), перенос
(гостевой и админский), создание блокировки. Замок отпускается сам при
commit/rollback. Конкурирующие операции выстраиваются в очередь — для
одного гостевого места это бесплатно.

- Создание/перенос брони: пересечение с активными бронями (как раньше,
  плюс страхует exclusion constraint) **и** с `blocked_periods` → 409
  `DATES_TAKEN`.
- Создание блокировки: пересечение с активными бронями (CONFIRMED и
  PENDING_OTP — у pending даты тоже удержаны) → 409 `OVERLAPS_BOOKING`
  со списком конфликтов `{bookingId, guestName, checkIn, checkOut}`.
  Каскадов нет: админ сам отменяет/переносит мешающие брони и повторяет.

## 4. API

### Публичное

- `POST /api/access-requests` `{phone, name, message?}` → 201.
  Rate limit по IP (по образцу `LoginRateLimiter`). Номер уже в белом
  списке (живой) → 409 `ALREADY_MEMBER`. Той же транзакцией — событие
  `ACCESS_REQUEST_RECEIVED` админу в outbox (если у админа нет
  `telegram_chat_id` — событие не пишем, заявка всё равно в админке).

### Админское (`/api/admin/**`)

Две линии обороны: URL-правило `hasRole("ADMIN")` (уже есть, этап 2) +
`@EnableMethodSecurity` и `@PreAuthorize("hasRole('ADMIN')")` на
админ-контроллерах. `AccessDeniedException` → 403 `FORBIDDEN` отдельным
хендлером (иначе catch-all даст 500).

- **Брони:** `GET /api/admin/bookings` — все брони с именами гостей,
  сортировка по датам; `POST /api/admin/bookings/{id}/cancel` — CONFIRMED
  или PENDING_OTP → CANCELLED, `cancelled_by = ADMIN`;
  `POST /api/admin/bookings/{id}/reschedule` `{checkIn, checkOut}` — без
  OTP, применяется сразу, проверки дат как в §3. Гостю — событие
  (`BOOKING_CANCELLED`/`BOOKING_RESCHEDULED` с `by: ADMIN`).
- **Блокировки:** `GET /api/admin/blocked-periods`;
  `POST /api/admin/blocked-periods` `{startDate, endDate, reason?}` → 201
  или 409 (§3); `DELETE /api/admin/blocked-periods/{id}` → 204.
- **Белый список:** `GET /api/admin/users` (активные; удалённые — с
  пометкой); `POST /api/admin/users` `{phone, name}` — ручное добавление
  друга без заявки (дубль живого номера → 409 `ALREADY_MEMBER`,
  удалённый — реактивация); `DELETE /api/admin/users/{id}` — soft delete;
  активная бронь (CONFIRMED/PENDING_OTP в будущем) → 409
  `ACTIVE_BOOKING_EXISTS`, сначала отмени бронь. Себя удалить нельзя
  (админ — тоже user) → 409.
- **Заявки:** `GET /api/admin/access-requests?status=` (по умолчанию
  PENDING); `POST /api/admin/access-requests/{id}/approve` — заявка →
  APPROVED, пользователь создан/реактивирован (роль FRIEND); новичка не
  уведомляем — владелец скажет сам, тот придёт в бота и получит WELCOME
  (этап 3); `POST /api/admin/access-requests/{id}/reject` → REJECTED.
  Уже решённая заявка → 409.

### Гостевая доработка (перенос из ревью этапа 4)

`DELETE /api/bookings/pending` — явная отмена своей PENDING_OTP-брони:
даты освобождаются сразу, челлендж вытесняется, не ждём чистильщика.
Плюс честный текст `OVERLAPS_OWN` для случая «мешает собственная
pending-бронь» (сейчас 409 с ложным текстом).

## 5. События и бот

- Новое событие `notifications.outbound`: `ACCESS_REQUEST_RECEIVED`
  `{chat_id, name, phone, message}` (админу).
- `BOOKING_CANCELLED` / `BOOKING_RESCHEDULED` получают поле
  `by: GUEST | ADMIN`; бот выбирает текст («…отменена владельцем» для
  ADMIN). Механика outbox/дедупа — без изменений (этап 3).
- Бот (consumer.go): рендер `ACCESS_REQUEST_RECEIVED`; все даты в
  сообщениях — по-русски: «с 22 марта 2026 по 25 марта 2026» (пожелание
  владельца). Внутри системы (БД/API/события) даты остаются ISO,
  русификация — только в текстах бота.

## 6. Ошибки

- Доменные not-found исключения на каждую сущность (бронь, блокировка,
  заявка, пользователь) → 404 со своим кодом и честным текстом. Убираем
  глобальный маппинг `EmptyResultDataAccessException` → «Бронь не
  найдена».
- `AccessDeniedException` → 403 `FORBIDDEN` (хендлер выше catch-all).
- `/api/me` (и любой защищённый роут) с валидным JWT удалённого
  пользователя → 401 + затирающая cookie (сейчас 500).
- Новые 409-коды: `OVERLAPS_BOOKING` (со списком конфликтов),
  `ALREADY_MEMBER`, `ACTIVE_BOOKING_EXISTS`.
- Мелочи попутно: `POST /api/bookings` → 201 (было 200), resend-code
  проверяет статус брони.

## 7. Тестирование

- Интеграционные (Testcontainers, существующая база `AbstractIntegrationTest`;
  новых таблиц нет — TRUNCATE-список не трогаем):
  блокировки (CRUD, 409 со списком конфликтов, бронь поверх блокировки →
  409); админ-отмена/перенос (статусы, `cancelled_by`, outbox-события с
  `by: ADMIN`, перенос на занятые/заблокированные даты → 409); белый
  список (soft delete → логин 401, старый JWT → 401 + затёртая cookie,
  удаление с активной бронью → 409, реактивация с историей броней);
  заявки end-to-end (POST → outbox-событие админу → approve → создан
  FRIEND → может логиниться; идемпотентный повтор; reject; повторное
  решение → 409); rate limit формы; 403 для FRIEND на `/api/admin/**`.
- Прямой тест `BlockedPeriodRepository.findOverlapping` (перенос из
  ревью этапа 1).
- Тест гонки: два потока одновременно «бронь vs блокировка» на одни даты —
  advisory lock пропускает ровно одного. Учебный гвоздь этапа.
- Go: юнит-тесты рендера `ACCESS_REQUEST_RECEIVED` и русских дат.

## 8. Разбивка на сессии (~1 час, каждая заканчивается зелёными тестами)

1. Фундамент: advisory lock + проверка блокировок в create/reschedule;
   доменные not-found; `AccessDeniedException` → 403; тест
   `findOverlapping`.
2. Блокировки: CRUD + конфликты + тест гонки.
3. Админ-брони: список, отмена, перенос + события с `by`.
4. Белый список: soft delete со всеми последствиями (401 + cookie,
   реактивация), ручное добавление; `DELETE /api/bookings/pending` +
   `OVERLAPS_OWN`.
5. Заявки: форма + rate limit + approve/reject + событие + бот (рендер,
   русские даты).
6. Учебный файл `docs/learning/05-admin-api-authorization.md` (роли и
   method security в Spring Security, advisory locks, soft delete,
   проектирование админ-API — тутор-формат с якорями кода), финальное
   ревью, PR.

## 9. Темы docs/learning/05

Роли и авторизация в Spring Security (URL-правила vs method security,
две линии обороны, путь `AccessDeniedException`); advisory locks в
Postgres (зачем, когда exclusion constraint не спасает, xact-вариант);
soft delete и его хвосты (уникальность, реактивация, фильтрация живых);
проектирование админ-API (без каскадов: 409 + явные действия админа).
