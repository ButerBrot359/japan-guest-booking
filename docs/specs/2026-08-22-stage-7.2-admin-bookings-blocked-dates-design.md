# Этап 7.2 — Админка: брони и блокировки дат

**Дата:** 2026-08-22
**Тип:** architectural (новый фронтовый флоу в админ-панели; backend-API готов с этапа 5)
**Область:** только фронтенд (`frontend/`)

## Цель

Дать владельцу в веб-админке два рабочих экрана:

1. **Брони** — видеть активные брони гостей, отменять их и переносить на другие даты.
2. **Блокировки** — закрывать периоды для гостей (ремонт, личные поездки), видеть список закрытий и снимать их.

Всё поверх уже существующих admin-эндпоинтов (этап 5). Backend не трогаем.

Философия этапа: **функционально и просто**. Глубокая UI/UX-полировка отложена на будущий проход — здесь важно, чтобы владелец мог реально управлять бронями и датами.

## Готовый backend (проверено, не меняем)

### Брони — `AdminBookingController` (`/api/admin/bookings`)
- `GET /api/admin/bookings` → `BookingRow[]`, где
  `BookingRow(long id, String guestName, String guestPhone, LocalDate checkIn, LocalDate checkOut, BookingStatus status, String comment)`.
  Возвращает **все** брони независимо от статуса (CONFIRMED / CANCELLED / COMPLETED). Фильтрация — на клиенте.
- `POST /api/admin/bookings/{id}/cancel` → `204`.
  Отменяет только `CONFIRMED`. Если уже отменена → `BookingExpiredException` (409, код `BOOKING_EXPIRED`). Шлёт гостю уведомление `BOOKING_CANCELLED` (by ADMIN).
- `POST /api/admin/bookings/{id}/reschedule` тело `{checkIn, checkOut}` (`LocalDate`, оба `@NotNull`) → `204`.
  Правила сервера:
  - `checkIn < checkOut` и `checkIn >= сегодня(JST)`, иначе `InvalidBookingDatesException` (код `VALIDATION_ERROR` / `INVALID_DATES` — уточняется по факту в хендлере).
  - **Лимита в 14 ночей НЕТ** (в отличие от гостевого создания).
  - Пересечение с блокировкой или чужой бронью → `DatesTakenException` (409, код `DATES_TAKEN`).
  - Переносить можно только `CONFIRMED`; иначе `BookingExpiredException`.
  - Шлёт гостю `BOOKING_RESCHEDULED` (by ADMIN).

### Блокировки — `AdminBlockedPeriodController` (`/api/admin/blocked-periods`)
- `GET /api/admin/blocked-periods` → `PeriodResponse[]`, где
  `PeriodResponse(long id, LocalDate startDate, LocalDate endDate, String reason, Instant createdAt)`.
  Отсортировано по `startDate`.
- `POST /api/admin/blocked-periods` тело `{startDate, endDate, reason?}` (`startDate`/`endDate` `@NotNull`, `reason` `@Size(max=200)`) → `201` + `PeriodResponse`.
  Правила сервера:
  - `endDate >= startDate`, иначе валидационная ошибка.
  - Пересечение с активной бронью → `OverlapsBookingException` (код уточняется в хендлере, вероятно `DATES_TAKEN`/`OVERLAPS_BOOKING`).
  - **Лимита длины НЕТ.**
- `DELETE /api/admin/blocked-periods/{id}` → `204`. Нет периода → `BlockedPeriodNotFoundException`.

### Важная семантика дат (проверено в `CalendarService`)
- Блокировка проецируется на календарь **включительно**: цикл `for (d = startDate; !d.isAfter(endDate); d++)`.
  То есть блок `startDate=10, endDate=12` закрывает дни 10, 11, 12 (три дня).
- Бронь с этапа 6.6 тоже занимает диапазон **включительно** (день выезда занят).
- Значит гостевой `Selection {checkIn, checkOut}` (где занят и `checkOut`) отображается на блокировку `startDate=checkIn, endDate=checkOut` **один-к-одному** без off-by-one.

      qc.invalidateQueries({ queryKey: ['calendar'] })

## Параметризация `pickDay` (`lib/selection.ts`)

Гостевое поведение — лимит 14 ночей, одиночный день запрещён. Для админа лимита нет; для блокировок нужен выбор одного дня.

```ts
export interface PickOptions {
  maxNights?: number       // по умолчанию 14
  allowSingleDay?: boolean // по умолчанию false
}

export function pickDay(
  selection: Selection,
  dayIso: string,
  days: Map<string, CalendarDay>,
  opts: PickOptions = {},
): Selection {
  const { maxNights = 14, allowSingleDay = false } = opts
  const { checkIn, checkOut } = selection
  if (!checkIn || checkOut) return { checkIn: dayIso, checkOut: null }
  // повторный клик по тому же дню — одиночный день (только если разрешён)
  if (dayIso === checkIn) return allowSingleDay ? { checkIn, checkOut: checkIn } : { checkIn: dayIso, checkOut: null }
  if (dayIso < checkIn) return { checkIn: dayIso, checkOut: null }
  if (nightsBetween(checkIn, dayIso) > maxNights) return { checkIn: dayIso, checkOut: null }
  const blocked = [...isoRange(checkIn, dayIso), dayIso]
    .some((d) => (days.get(d)?.status ?? 'FREE') !== 'FREE')
  return blocked ? { checkIn: dayIso, checkOut: null } : { checkIn, checkOut: dayIso }
}
```

Существующий вызов в `CalendarPage.tsx` (`pickDay(s, iso, days)`) не меняется — дефолты сохраняют поведение (14 ночей, без одиночного дня). Тест гостевого календаря остаётся зелёным.

**Замечание про single-day и `isoRange`:** при `checkOut === checkIn` подсветка в `Calendar` через `isoRange(checkIn, checkOut)` даст пустой диапазон, но `selection.checkOut` совпадает с `checkIn`, и множество `selected` в `Month` строится как `[...isoRange(checkIn, checkOut), checkOut]` → содержит сам день. Один день подсветится корректно. (Проверить в тесте пикера.)

## Компонент `DateRangePicker.tsx`

Оборачивает `Calendar`, держит состояние текущего месяца (мобильные 2 месяца + стрелки, десктоп несколько месяцев — как в `CalendarPage`), зовёт `pickDay` с нужными опциями. Показывает выбранный диапазон текстом и кнопку подтверждения.

```ts
interface DateRangePickerProps {
  days: Map<string, CalendarDay>       // занятость для отрисовки (из useCalendar, при необходимости с вырезанными днями)
  value: Selection
  onChange: (next: Selection) => void
  pickOptions?: PickOptions            // {maxNights, allowSingleDay}
  minMonth: string                     // первый выбираемый месяц (обычно текущий)
  monthsWindow?: number                // сколько месяцев показывать (по умолчанию как в CalendarPage)
}
```

Поведение:
- Внутренний `monthStart` (стартовое — `minMonth`), `shiftMonth(delta)` с границами (как `CalendarPage.shiftMonth`).
- Мобильные месяцы `[monthStart, addMonths(monthStart,1)]`, десктоп — окно из N месяцев от `minMonth`.
- `onPick(iso) → onChange(pickDay(value, iso, days, pickOptions))`.
- `maxCheckout`: только если `pickOptions.maxNights` конечен и `value.checkIn && !value.checkOut` — тогда `addDays(checkIn, maxNights)`; иначе не передаём (нет визуального ограничения хвоста).
- Не рендерит `onPickBusy` (в админе «кто гостит» не нужен; занятые дни просто disabled).

Компонент — «контролируемый»: состояние выбора (`value`) держит родитель (модалка переноса / форма блокировки), сам пикер владеет только навигацией по месяцам. Это упрощает тестирование и сброс.

## Вкладка «Брони» (`AdminBookings.tsx`)

Данные: `useAdminBookings()`. Клиентский фильтр «только активные»:

```ts
const today = todayIso()
const active = (data ?? []).filter((b) => b.status === 'CONFIRMED' && b.checkOut >= today)
```

(Ленивый COMPLETED: у прошедших броней в БД статус может остаться `CONFIRMED`, поэтому дополнительно отсекаем по `checkOut >= today`.)

Таблица (`data-testid="admin-bookings"`), колонки:
- Гость (`guestName`)
- Телефон (`guestPhone`)
- Даты (`isoToRu(checkIn) → isoToRu(checkOut)`)
- Ночей (`nightsBetween`)
- Комментарий (`comment ?? '—'`, обрезка + `title`)
- Действия: `[Перенести][Отменить]`

Пустое состояние: «Активных броней нет».

### Отмена
- Клик «Отменить» → confirm-модалка (как в `AdminGuests`): «Отменить бронь гостя {name} {даты}? Гость получит уведомление.»
- Подтверждение → `useAdminCancelBooking().mutate(id)`; при успехе закрыть модалку.
- Ошибка `BOOKING_EXPIRED` (409, уже отменена) → закрыть модалку тихо (список и так обновится через `onSettled`). Прочие ошибки → короткий текст «Не удалось отменить — попробуйте ещё раз».

### Перенос
- Клик «Перенести» → модалка с `DateRangePicker`.
- Занятость: берём `useCalendar(yearFrom, yearTo)` и **вырезаем дни самой этой брони**, чтобы админ мог сдвинуть её на пересекающийся диапазон:

```ts
const daysForReschedule = (calendarDays: Map<string, CalendarDay>, b: AdminBookingRow) => {
  const m = new Map(calendarDays)
  for (const d of [...isoRange(b.checkIn, b.checkOut), b.checkOut]) m.delete(d) // теперь эти дни FREE
  return m
}
```

- `pickOptions = { maxNights: Infinity, allowSingleDay: false }` (бэкенд не лимитирует ночи; бронь ≥1 ночи).
- Начальное `value` — пустое (`{checkIn:null, checkOut:null}`); подпись показывает текущие даты брони как контекст: «Сейчас: {даты}».
- Кнопка «Перенести» активна только когда `checkIn && checkOut`.
- Сабмит → `useAdminRescheduleBooking().mutate({id, checkIn, checkOut})`.
- Ошибка `DATES_TAKEN` → «Эти даты заняты — выберите другие.» Ошибка валидации → «Даты в прошлом или некорректны.» Успех → закрыть модалку.

### Создание
Форма над списком:
- `DateRangePicker` с `pickOptions = { maxNights: Infinity, allowSingleDay: true }`.
- Занятость — прямо из `useCalendar` (уже занятые/закрытые дни disabled: нельзя закрыть поверх брони — бэкенд отвергнет, а поверх существующей блокировки бессмысленно).

## Глобальные ограничения (для плана)

- Только фронтенд; backend и его тесты не трогаем.
- Гостевой `pickDay` и `CalendarPage` не должны сломаться — параметризация с дефолтами; существующие тесты остаются зелёными.
- Все команды фронта — из каталога `frontend/` (иначе vitest падает с «document is not defined»).
- Инвалидация `['calendar']` во всех мутациях, меняющих занятость (переносы, блокировки).
- Мутации, у которых 409 — нормальный исход (отмена уже отменённой), используют `onSettled` для обновления списка.
- Тексты — по-русски, тёплый тон проекта. Копи-полировка отложена, но заглушки/плейсхолдеры недопустимы.
- Коды ошибок (`DATES_TAKEN`, `BOOKING_EXPIRED`, валидация) читаются из `ApiError.code`; при реализации сверить фактические коды хендлеров бэкенда и поправить маппинг, если отличаются.
