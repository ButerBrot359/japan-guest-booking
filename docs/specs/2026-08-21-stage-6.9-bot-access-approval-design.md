# Этап 6.9 — Одобрение заявок админом через бота

Дата: 2026-08-21. Под-проект 2 из «интерактивного меню бота» (часть B UX-итерации),
на фундаменте этапа 6.8 (синхронный канал бот→бэкенд, служебный токен).

## Цель

Дать админу одобрять/отклонять заявки на доступ **кнопками прямо в чате с ботом** —
`[✅ Добавить]` / `[❌ Отклонить]` под уведомлением о заявке. Убрать curl из потока заявок.

## Не-цели

- Уведомление самого заявителя (его Telegram неизвестен — он подавал через сайт-форму;
  админ сам скажет ему зайти). Как в текущем `approve` (спека этапа 5, §4).
- Веб-админка для заявок (это этап 7). Веб-API `/api/admin/access-requests/**` остаётся
  без изменений — это параллельный путь.
- Действия над бронями/гостями через бота — вне объёма.

## Ключевое решение: канал действия

Первый **пишущий** синхронный вызов бот→бэкенд (в 6.8 канал был read-only). Вариант A
из брейншторминга (Kafka request/reply отвергнут — кнопке нужен мгновенный отклик):
новый эндпоинт на surface `/api/bot/**` (тот же `BOT_API_TOKEN`), **плюс** проверка внутри,
что нажавший — админ (по `admin_chat_id`).

## Бэкенд

### Событие `ACCESS_REQUEST_RECEIVED` получает `request_id`

Сейчас payload несёт `chat_id, name, phone, message`. Добавляем `request_id` (id заявки) —
он нужен боту, чтобы собрать кнопки `approve:<id>`/`reject:<id>`.

`AccessRequestService.submit` сейчас делает `insert ... on conflict do nothing` (jdbc.update,
возвращает count). Чтобы получить id вставленной заявки: заменить на
`insert ... on conflict (phone) where status='PENDING' do nothing returning id` через
`jdbc.query`/`queryForList` — при вставке вернётся ровно одна строка с id, при конфликте
строк нет (тогда, как сейчас, событие не пишем и не спамим). Полученный id кладём в событие
`ACCESS_REQUEST_RECEIVED` как `request_id`.

### Новый эндпоинт

`POST /api/bot/access-requests/{id}/approve` и `POST /api/bot/access-requests/{id}/reject`,
тело `{ "admin_chat_id": <long> }`:

- Защита `/api/bot/**` служебным токеном `X-Bot-Token` (существующий `BotTokenFilter`, роль BOT).
- **Дополнительно**: `admin_chat_id` резолвится через `findByTelegramChatIdAndDeletedAtIsNull`;
  если пользователя нет ИЛИ его роль не `ADMIN` → `403 FORBIDDEN`. (Защита в глубину: кнопки и
  так только в админском чате, но бэкенд не доверяет этому вслепую.)
- Дальше переиспользуем `AccessRequestService.approve(id)` / `reject(id)` без изменений их логики.
- Коды ответов боту:
  - `204` — успех;
  - `403 FORBIDDEN` — `admin_chat_id` не принадлежит живому ADMIN;
  - `404 NOT_FOUND` — заявки с таким id нет (`AccessRequestNotFoundException`, уже маплен);
  - `409 ALREADY_RESOLVED` — заявка уже не PENDING (`AlreadyResolvedException`, уже маплен) —
    кто-то одобрил/отклонил через сайт или другой админ раньше.

Контроллер — новый (например `BotAdminController` в пакете `bot`), `@RequestMapping("/api/bot")`.
Валидация тела: `admin_chat_id` `@NotNull`.

## Бот

### Inline-кнопки под уведомлением о заявке

В `consumer`, ветка `ACCESS_REQUEST_RECEIVED`: сообщение отправляется с inline-клавиатурой
из двух кнопок в один ряд:
- `✅ Добавить` → `callback_data = "approve:<request_id>"`
- `❌ Отклонить` → `callback_data = "reject:<request_id>"`

`callback_data` ≤ 64 байта (id — число, влезает с запасом). Дедуп события (`remember`) сохраняем.
Событие `events.AccessRequestReceived` в Go получает поле `RequestID int64` (`json:"request_id"`).

### Разбор `callback_query` (новый тип апдейта)

`getUpdates` возвращает апдейты, где вместо `message` может быть `callback_query`. Расширяем:
- `Update` получает поле `CallbackQuery *CallbackQuery`.
- `CallbackQuery{ ID string; From *User; Message *Message; Data string }` (Message несёт
  `chat.id` и `message_id` — они нужны для правки).
- `poller.handle`: если `u.CallbackQuery != nil` → `handleCallback`, иначе как сейчас (message).

### Обработка нажатия (`handleCallback`)

1. Разобрать `Data` = `"<action>:<id>"`, action ∈ {approve, reject}. Кривой формат → `answerCallbackQuery` с «не понял» и выход.
2. Позвать бэкенд `POST /api/bot/access-requests/{id}/<action>` с `admin_chat_id = callback.Message.Chat.ID`.
3. По результату:
   - `204` → `answerCallbackQuery` (короткий тост «Готово»), затем `editMessageText`: заменить
     текст на итог (`✅ Добавлен: Имя, +7…` / `❌ Отклонён: Имя`), кнопки убираются (edit без reply_markup).
   - `409` → `answerCallbackQuery` «уже обработана», `editMessageText` на «уже обработана».
   - `403` → `answerCallbackQuery` «недостаточно прав» (сообщение не трогаем).
   - сетевая ошибка/прочее → `answerCallbackQuery` «не получилось, попробуй ещё раз» (сообщение не трогаем).
4. Ошибки не фатальны для poller (offset двигается): callback не передоставляется как message,
   а действие approve идемпотентно (повтор → 409, без двойного добавления). `handle` для
   callback-ветки не возвращает ошибку.

Текст правки НЕ парсим — берём исходный текст сообщения (`callback.Message.Text`) и добавляем
сверху строку статуса: `✅ Добавлен\n\n<исходный текст заявки>` (или `❌ Отклонён\n\n…`). Так имя
и телефон сохраняются как есть, без разбора.

### Метод бот-клиента (internal/backend)

`internal/backend.Client` (из 6.8) получает пишущий метод:
`ResolveAccessRequest(ctx, id int64, action string, adminChatID int64) (int, error)` —
`POST /api/bot/access-requests/{id}/{action}` с телом `{admin_chat_id}` и заголовком `X-Bot-Token`;
возвращает HTTP-статус (204/403/404/409) для маршрутизации ответа в `handleCallback`, либо ошибку сети.

### Новые методы телеграм-клиента

- Отправка сообщения с inline-кнопками (для `ACCESS_REQUEST_RECEIVED`): `reply_markup.inline_keyboard`.
- `AnswerCallback(ctx, callbackID, text)` → `answerCallbackQuery`.
- `EditMessageText(ctx, chatID, messageID, text)` → `editMessageText` (без reply_markup — убирает кнопки).

Все три — через существующий приватный `post`. Интерфейсы `Sender` (consumer) и/или API (poller)
расширяются соответствующими методами.

## Обработка краёв (сводка)

| Ситуация | Ответ |
|---|---|
| Успех approve/reject | тост «Готово» + правка: `✅ Добавлен`/`❌ Отклонён` + исходный текст, кнопки убраны |
| Заявка уже не PENDING (409) | тост «уже обработана» + правка сообщения |
| `admin_chat_id` не ADMIN (403) | тост «недостаточно прав», сообщение не трогаем |
| Кривой `callback_data` | тост «не понял», выход |
| Сетевая ошибка к бэкенду | тост «попробуй ещё раз», сообщение не трогаем |
| Два админа жмут одну заявку | первый — успех, второй — 409 «уже обработана» |

## Тестирование

**Бэкенд (Testcontainers):**
- `approve` с админским `admin_chat_id` → заявка APPROVED + телефон в белом списке; `204`.
- `reject` → заявка REJECTED; `204`.
- `admin_chat_id` не принадлежит ADMIN (гость или неизвестный) → `403`.
- Заявка уже обработана → `409 ALREADY_RESOLVED`.
- Нет `X-Bot-Token` → `401`.
- `AccessRequestService.submit` кладёт `request_id` в событие `ACCESS_REQUEST_RECEIVED`.

**Бот (Go):**
- `consumer` шлёт `ACCESS_REQUEST_RECEIVED` с inline-кнопками `approve:<id>`/`reject:<id>`.
- Разбор `callback_query` из getUpdates.
- `handleCallback`: 204 → answer+edit; 409 → answer+edit «уже обработана»; 403 → answer «нет прав»,
  без edit; сетевой сбой → answer «попробуй ещё раз».
- Клиент: inline-кнопки, `AnswerCallback`, `EditMessageText`, `ResolveAccessRequest` через httptest.
- Регрессия: существующие тесты poller/consumer/клиента зелёные после расширения.

## Конфигурация

Ничего нового: используется существующий `BOT_API_TOKEN` и `BACKEND_URL` из этапа 6.8.

## Порядок работ

1. Бэкенд: `request_id` в событие; `BotAdminController` (approve/reject) с проверкой ADMIN по chat_id; тесты.
2. Бот: событие `AccessRequestReceived.RequestID`; методы клиента (inline, answerCallback, editMessageText); тесты клиента.
3. Бот: inline-кнопки в `consumer` для `ACCESS_REQUEST_RECEIVED`; тест.
4. Бот: разбор `callback_query` + `handleCallback` в poller + бэкенд-клиент-вызовы; тесты.
5. Живой смоук: заявка с сайта → кнопки в боте → нажатие → белый список / статус.
