# Этап 6.8 — Гостевое меню в боте (read-only)

Дата: 2026-08-21. Под-проект 1 из «интерактивного меню бота» (часть B UX-итерации).
Второй под-проект — одобрение заявок админом через бота — отдельная спека позже,
на том же фундаменте.

## Цель

Дать гостю в Telegram постоянные кнопки «📋 Мои записи» и «🗺 История», по нажатию
на которые бот показывает его активную бронь и завершённые поездки красиво, с эмодзи.
Только показ — без действий (отмена/перенос/комментарий остаются на сайте).

## Не-цели

- Никаких действий из бота (отмена/перенос/комментарий) — кнопка «Открыть сайт» не нужна
  в этом под-проекте (можно добавить позже).
- Админское одобрение заявок — следующий под-проект.
- Inline-кнопки под конкретными сообщениями и командное меню Telegram — не используем;
  выбран формат постоянной reply-клавиатуры.

## Ключевое архитектурное решение: канал бот→бэкенд

Сегодня бот — «мост Telegram ↔ Kafka, бизнес-логики нет»: `poller` публикует события
в Kafka, `consumer` рассылает уведомления. Кнопка требует **синхронного** ответа на
нажатие, поэтому вводим **первый синхронный HTTP-вызов бот→бэкенд** (вариант A из
брейншторминга; Kafka request/reply отвергнут как оверкилл для read-only).

- Новый защищённый surface `/api/bot/**` на бэкенде, аутентификация по служебному токену
  `BOT_API_TOKEN` (общий секрет в `.env`), **отдельно от JWT-кук гостя**.
- Kafka-канал уведомлений (`notifications.outbound`, `telegram.inbound`) не меняется.

## Бэкенд

### Эндпоинт

`GET /api/bot/bookings?chat_id=<id>` → `200`:

```json
{ "linked": true,
  "active": { "checkIn": "2026-03-12", "checkOut": "2026-03-15", "status": "CONFIRMED" },
  "history": [ { "checkIn": "2025-06-01", "checkOut": "2025-06-04", "nights": 3 } ] }
```

- `chat_id` резолвится в гостя по `users.telegram_chat_id` (живого: `deleted_at is null`).
- Гостя нет → `200 { "linked": false, "active": null, "history": [] }` (не 404 — «не привязан»
  это нормальный ответ, а не ошибка; бот отличает его от сетевого сбоя по HTTP-статусу).
- `active`: активная бронь (`CONFIRMED`, иначе `null`) с полями `checkIn/checkOut/status`.
  Комментарий НЕ отдаём (в боте не показываем).
- `history`: завершённые поездки (`COMPLETED`), свежие сверху, с `nights`.
- Валидация: отсутствует `chat_id` → `400 VALIDATION_ERROR`.

### Аутентификация

- `BotTokenFilter` (перед `JwtAuthFilter`): для путей `/api/bot/**` читает заголовок
  `X-Bot-Token`; совпал с `app.bot.api-token` → выставляет `Authentication` с ролью `BOT`;
  иначе — пропускает без аутентификации (SecurityConfig затем вернёт 401).
- `SecurityConfig`: `.requestMatchers("/api/bot/**").hasRole("BOT")` (перед `/api/**`).
- `app.bot.api-token` из env `BOT_API_TOKEN`. Если не задан — эндпоинт закрыт (токен-заголовок
  никогда не совпадёт с пустым/несконфигурированным; фильтр не аутентифицирует → 401).
  Значение `null`/blank в конфиге трактуется как «не задан».

### Переиспользование сборки броней

Логика «активная бронь + история завершённых» сейчас живёт в `MeController.myBookings`.
Выносим её в общий метод (сервис), которым пользуются и `MeController`, и `BotController`,
чтобы не дублировать запрос. `BotController` строит из него ответ без поля `comment`.

## Бот

### Пакет `internal/backend`

HTTP-клиент к бэкенду:
- `NewClient(baseURL, token string)`.
- `GetGuestBookings(ctx, chatID int64) (GuestBookings, error)` — `GET {base}/api/bot/bookings?chat_id=`,
  заголовок `X-Bot-Token: <token>`. Таймаут ~10с.
- Возвращает `GuestBookings{ Linked bool; Active *Booking; History []Visit }`.
  Не-2xx → ошибка (бот отвечает «попробуй позже»).

### Меню-клавиатура

- Постоянная reply-клавиатура: ряд из двух кнопок «📋 Мои записи», «🗺 История»
  (`resize_keyboard: true`, `is_persistent: true`, БЕЗ `one_time_keyboard`).
- Показывается: (1) при привязке — `consumer` прикладывает её к сообщению `WELCOME`;
  (2) на `/start` от уже привязанного гостя.
- Обобщаем отправку сообщения телеграм-клиента, чтобы прикладывать разные `reply_markup`
  (контакт-кнопка для `/start` анонима, меню для привязанного). Сейчас `SendMessage` несёт
  `requestContact bool` — заменяем на явную модель разметки (contact / menu / без разметки),
  чтобы не плодить булевы флаги.

### Роутинг и рендер

- `poller` при тексте сообщения `«📋 Мои записи»` или `«🗺 История»` вызывает бэкенд-клиент
  и шлёт отформатированный ответ. Логика форматирования — в отдельном компоненте (не в poller).
- `/start`: всегда показывает приглашение поделиться контактом с контакт-кнопкой (как сейчас);
  меню-клавиатуру на `/start` НЕ шлём — бот на этом этапе не знает, привязан ли chat_id, а гонять
  его в бэкенд на каждый `/start` не нужно. Меню появляется один раз при привязке (`WELCOME`) и
  дальше висит в клиенте (reply-клавиатура персистентна).
- Нажатия кнопок обрабатываются независимо от `/start`: если гость жмёт «Мои записи», а бэкенд
  вернул `linked:false` — бот отвечает «Сначала поделись контактом — нажми /start». Так
  привязанность проверяется по факту нажатия, отдельного состояния в боте не нужно.

### Формат сообщений (эмодзи, русский, тон «ты»)

- Активная бронь, статус CONFIRMED:
  `📋 Твоя бронь: 12 марта 2026 → 15 марта 2026\n✅ подтверждена`
- Нет активной брони:
  `Пока нет активной брони. Выбери даты на сайте 🗓`
- История (заголовок + строки):
  `🗺 Твои поездки:\n🏡 1 июня 2025 → 4 июня 2025 · 3 ночи\n🏡 ...`
- Пустая история: `Пока нет завершённых поездок 🏡`
- Не привязан (кнопка без контакта): `Сначала поделись контактом — нажми /start 📲`
- Ошибка бэкенда: `Не получилось загрузить, попробуй позже 🙏`
- Русские даты — существующий `ruDate`; склонение «ночь/ночи/ночей» — новый хелпер в боте
  (зеркало фронтового `nightsWord`).

## Обработка краёв

| Ситуация | Ответ бота |
|---|---|
| `linked:false` | «Сначала поделись контактом — нажми /start» |
| `active:null` | «Пока нет активной брони. Выбери даты на сайте» |
| пустая `history` | «Пока нет завершённых поездок» |
| HTTP-ошибка/таймаут | «Не получилось загрузить, попробуй позже» |
| текст совпал с кнопкой случайно | обрабатываем как нажатие — приемлемо (редко) |

## Конфигурация

- `BOT_API_TOKEN` — новый общий секрет в корневом `.env`; прокинуть в сервисы
  `backend` и `bot` в `docker-compose.dev.yml`.
- Бот получает `BACKEND_URL` (в compose — `http://backend:8080`) для HTTP-клиента.
- Локально без Docker: те же env-переменные.

## Тестирование

**Бэкенд (Testcontainers):**
- Валидный `X-Bot-Token` + привязанный гость → `linked:true`, верные active/history.
- Неизвестный `chat_id` → `linked:false`.
- Нет заголовка / неверный токен → `401`.
- Отсутствует `chat_id` → `400`.
- Гость с активной CONFIRMED и парой COMPLETED — проверка порядка истории и полей.

**Бот (Go):**
- `internal/backend` клиент через `httptest`: успех, 401, 5xx, таймаут.
- Форматирование: активная/нет-активной, история/пустая, склонение ночей, эмодзи.
- Роутинг poller: текст «📋 Мои записи»/«🗺 История» → вызов клиента и отправка ответа;
  не-привязан → подсказка про /start.
- Меню-клавиатура прикладывается к `WELCOME` (consumer) и на `/start`.
- Регрессия: существующие тесты poller/consumer/клиента зелёные после обобщения разметки.

**Конфиг:** проброс env в compose проверяется живым смоуком (стек на :3000).

## Порядок работ

1. Бэкенд: общий метод сборки броней, `BotController`, `BotTokenFilter`, SecurityConfig, тесты.
2. Бот: `internal/backend` клиент + тесты.
3. Бот: обобщение разметки телеграм-клиента (contact/menu/none), меню на WELCOME/start.
4. Бот: рендер гостевого меню + роутинг в poller + тесты.
5. Конфиг: `BOT_API_TOKEN`/`BACKEND_URL` в .env и compose; живой смоук.
