# Этап 7.1 — Веб-админка: фундамент + заявки + гости

Дата: 2026-08-22. Под-проект 1 из трёх для веб-админки (этап 7). Следующие под-проекты
(отдельные спеки): 7.2 брони + блокировки дат; 7.3 выгрузка в Excel.

## Цель

Дать владельцу веб-раздел администратора под `/admin`: вход по паролю, guard, оболочку
с навигацией и две самые ходовые области — **заявки на доступ** (одобрить/отклонить) и
**гости/белый список** (добавить/удалить, редактировать приветствия). Убрать необходимость
дёргать admin-API руками через curl.

## Не-цели

- Брони, блокировки дат, выгрузка в Excel — следующие под-проекты (7.2, 7.3).
- Мобильная адаптация: **только десктоп** (админка используется с компа). На телефоне
  откроется, просто узко — отдельной вёрстки под мобилу нет.
- Изменение существующего admin-API (кроме одной добавки — GET приветствий, см. ниже).
- Одобрение заявок через бота (это этап 6.9, уже готово) — веб-путь параллельный.

## Что уже готово (не трогаем)

Admin-API этапа 5 полностью на месте:
- `POST /api/auth/admin-login {phone, password}` → кука (роль ADMIN).
- `GET /api/admin/access-requests?status=PENDING|APPROVED|REJECTED`, `POST .../{id}/approve`, `.../{id}/reject`.
- `GET /api/admin/users` → `UserRow(id, phone, name, role, telegramLinked, deletedAt)`,
  `POST /api/admin/users {phone, name}` (201; 409 ALREADY_MEMBER), `DELETE /api/admin/users/{id}` (204, soft),
  `PUT /api/admin/users/{id}/greetings {greetings: [...]}` (204).
- `/api/admin/**` под `hasRole("ADMIN")` (SecurityConfig); `/api/me` отдаёт `role` (FRIEND|ADMIN).

## Backend — единственная добавка

`GET /api/admin/users/{id}/greetings` → `200 ["текст 1", "текст 2"]` (текущие приветствия гостя,
в порядке хранения). Нужен, чтобы редактор приветствий показывал существующие значения (сейчас
есть только PUT, перезаписывающий весь набор вслепую).

- Реализация: `WhitelistService.greetings(long id): List<String>` (читает `UserGreetingRepository`
  по userId, отдаёт тексты); новый метод в `AdminUserController`: `@GetMapping("/{id}/greetings")`.
- Гость не найден → пустой список (не 404): отсутствие приветствий — нормальное состояние.
- Под `hasRole("ADMIN")` автоматически (matcher `/api/admin/**`).

## Фронтенд

### Роутинг и вход

- Новый роут `/admin` в `App.tsx` → `AdminPage`.
- `AdminPage` — guard: тянет `useMe()`; пока грузится — ничего; `role === 'ADMIN'` → панель;
  иначе → `AdminLoginCard`.
- `AdminLoginCard` — форма телефон (маска, как в гостевом `LoginCard`) + пароль; сабмит →
  `useAdminLogin` (`POST /api/auth/admin-login`); onSuccess инвалидирует `['me']` → guard
  перерисовывается в панель. Ошибка `INVALID_CREDENTIALS` → «Неверный телефон или пароль».
- Выход — `useLogout()` (существующий), инвалидирует `['me']` → назад к форме.

### Оболочка `AdminPage`

- Десктоп-контейнер (`max-w-5xl mx-auto`, тема «Тёплая бумага»).
- Шапка: заголовок «Админка», кнопка «выйти».
- Вкладки навигации (in-page state, без вложенных роутов): **[Заявки] [Гости]**.
- Рендерит активную секцию.

### Секция «Заявки» (`AdminAccessRequests`)

- Под-вкладки **Ожидающие / История** (state).
- Ожидающие (`useAccessRequests('PENDING')`): строки (имя, телефон, комментарий, дата) с кнопками
  «Добавить» (`useApproveRequest`) и «Отклонить» (`useRejectRequest`). После действия — инвалидация
  `['admin','access-requests']`; строка уходит из списка.
- История: маленький переключатель статуса **Одобренные / Отклонённые** (один запрос за раз —
  `useAccessRequests('APPROVED')` либо `'REJECTED'`), только чтение: имя, телефон, статус, дата решения.
- Край: заявка уже обработана (409 ALREADY_RESOLVED) → тихо инвалидируем список (кто-то решил через бота/сайт).

### Секция «Гости» (`AdminGuests`)

- Таблица (`useAdminGuests` → `GET /api/admin/users`): имя, телефон, роль, Telegram (да/нет),
  статус (активен / удалён по `deletedAt`). Сортировка по id (как отдаёт API).
- «Добавить гостя»: форма телефон (маска) + имя → `useAddGuest` (`POST /api/admin/users`);
  409 ALREADY_MEMBER → «Этот номер уже в списке».
- По строке активного гостя: «Удалить» (диалог подтверждения → `useDeleteGuest` `DELETE`),
  «Приветствия» (открывает редактор). У удалённых — кнопок действий нет (помечены «удалён»).
- Редактор приветствий (модалка/панель): при открытии `useGuestGreetings(id)` грузит текущие;
  список строк с «удалить» на каждой и «добавить строку»; «Сохранить» → `useSetGreetings`
  (`PUT .../greetings`), инвалидирует greetings этого гостя. Пустой список — уберёт приветствия.

### API-слой (`api/queries.ts`, `api/types.ts`)

Новые хуки (все GET/мутации через существующий `api`-клиент, кука ходит сама):
- `useAdminLogin()` — `POST /auth/admin-login {phone, password}`; onSuccess инвалидирует `['me']`.
- `useAccessRequests(status: 'PENDING'|'APPROVED'|'REJECTED')` — `GET /admin/access-requests?status=`;
  ключ `['admin','access-requests', status]`.
- `useApproveRequest()`, `useRejectRequest()` — `POST /admin/access-requests/{id}/approve|reject`;
  onSuccess инвалидируют `['admin','access-requests']`.
- `useAdminGuests()` — `GET /admin/users`; ключ `['admin','users']`.
- `useAddGuest()`, `useDeleteGuest()` — `POST /admin/users` / `DELETE /admin/users/{id}`;
  onSuccess инвалидируют `['admin','users']`.
- `useGuestGreetings(id)` — `GET /admin/users/{id}/greetings`; ключ `['admin','greetings', id]`.
- `useSetGreetings()` — `PUT /admin/users/{id}/greetings {greetings}`; onSuccess инвалидирует
  `['admin','greetings', id]`.

Типы (зеркало backend): `AdminUserRow { id, phone, name, role, telegramLinked, deletedAt }`,
`AccessRequestRow { id, phone, name, message, status, createdAt, resolvedAt }`.

## Обработка краёв (сводка)

| Ситуация | Поведение |
|---|---|
| Неверный пароль админа (401 INVALID_CREDENTIALS) | «Неверный телефон или пароль» |
| Не-ADMIN зашёл на /admin | Форма входа админа |
| Добавить существующего гостя (409 ALREADY_MEMBER) | «Этот номер уже в списке» |
| Заявка уже обработана (409 ALREADY_RESOLVED) | Тихо обновить список |
| Пустой набор приветствий | Сохранить как «нет приветствий» |

## Тестирование

**Backend (Testcontainers):**
- `GET /api/admin/users/{id}/greetings` возвращает текущие приветствия (порядок хранения);
  гость без приветствий → пустой список; без ADMIN-куки → 401/403.

**Фронтенд (vitest + MSW):**
- Guard: `/api/me` роль FRIEND/аноним → форма входа; ADMIN → панель.
- Вход по паролю: успешный → панель; неверный → сообщение.
- Заявки: список ожидающих; «Добавить»/«Отклонить» → строка уходит; переключение Ожидающие/История.
- Гости: список; добавить (успех + 409); удалить (подтверждение); редактор приветствий
  (загрузка текущих, добавление/удаление строк, сохранение).

## Конфигурация

Ничего нового. Пароль/телефон админа — существующие `app.admin.*` (dev-заглушки; боевые — этап 8).

## Порядок работ

1. Backend: `WhitelistService.greetings` + `AdminUserController` GET-эндпоинт + тест.
2. Фронт: API-слой (queries/types) для admin.
3. Фронт: `AdminLoginCard` + `AdminPage` (guard, оболочка, вкладки) + роут `/admin`.
4. Фронт: секция «Заявки» (ожидающие/история, approve/reject).
5. Фронт: секция «Гости» (таблица, добавить/удалить, редактор приветствий).
6. Живой смоук: вход админом, заявки, гости, приветствия.
